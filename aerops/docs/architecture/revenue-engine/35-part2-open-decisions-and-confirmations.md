> **Status:** Proposed — Phase 8 Part 2 · **Date:** 2026-07-10 · **Lead roles:** Head of Product; Flight School Owner; Reliability/SRE Engineer · **Part of:** Revenue Engine design set ([README](./README.md))

This document carries Part 2 deliverables 19 and 20 (§5) and closes the Part 2 design set the way [16-risks-and-open-decisions.md](./16-risks-and-open-decisions.md) closed Part 1. It **extends** Part 1's register — it does not duplicate it and it does not reopen anything doc 16 or [13-database-model.md](./13-database-model.md) already closed. It contains:

- **§2** — the resolution status of every Part 1 open decision that Part 2 engaged with (answered, partially answered, or escalated), with pointers to the answering doc.
- **§3** — the **new** open decisions Part 2 raised, deduplicated across docs 17–34, prioritized, each with options, a recommendation, and a named decider. Numbering continues doc 16's register (D45+) so the combined set reads as one list.

- **§5** — the compliance confirmations the spec requires (deliverables 19–20), plus the standing-constraint statement.
- **§6** — the Part 2 deliverables map (1–20).

Simpler-workflow choice: the 40+ raw open questions scattered across docs 17–34 are consolidated here into 25 decision rows, **bundled by the meeting that decides them** — one commercial call (CEO), one legal package (counsel), one pilot-operations call (SRE + product) — so the owner works a single prioritized list, not eleven appendices. Every source question is cited; nothing was dropped in the merge.

## 5. Compliance confirmations (Deliverables 19–20)

### 5.1 Deliverable 19 — no live charges occurred, and none are possible

No live charges occurred, and none are possible from this design phase. Phase 8 Part 2 created **no Stripe objects of any kind** — no platform account, no connected account, no customer, no PaymentIntent, no SetupIntent, no webhook endpoint, no API key. No Stripe SDK, dependency, or provider reference was added to the codebase. **Stripe test mode is the only sanctioned environment for Parts 2–3, and even test mode remains unexercised** — Part 2 is paper design. Charging remains behind the `REVENUE_CHARGING` flag, which defaults off and whose only sanctioned value in this phase is `test`; live mode is additionally gated on the approved threat model ([32-financial-security-threat-assessment.md](./32-financial-security-threat-assessment.md)) and the qualified legal/accounting review required by ADR-037 ([18-stripe-connect-decision.md](./18-stripe-connect-decision.md)) — both stated in that ADR as non-skippable.

### 5.2 Deliverable 20 — nothing was deployed

Nothing was deployed. Phase 8 Part 2 produces markdown design documents in `docs/architecture/revenue-engine/` (docs 17–35) and nothing else. `prisma/schema.prisma`, application source, `package.json`, and all configuration are unchanged. No migration was generated or run. No dependency was installed. No infrastructure, environment variable, deployment target, or external service was touched or provisioned.

### 5.3 No production emails were sent

No production emails were sent, and none can be: no email provider exists in the codebase. [31-notifications.md](./31-notifications.md) designs the email seam **dormant** — `NotificationEmailStatus` records `NOT_CONFIGURED`/`PREVIEWED` truthfully, `SENT`/`FAILED` are reserved values with no Part 2 writer, and the dev console preview refuses to run in production. The design never claims email was sent when it was not, and the existing notifications-page copy that overstated email/SMS capability is corrected rather than perpetuated.

### 5.4 Part 1 requirements were not reinterpreted or weakened

Part 1 remains binding. Every Part 2 doc **extends Part 1 by filename reference** — [13-database-model.md](./13-database-model.md) stays canonical for all Part 1 model, enum, and status names, and [34-part2-database-additions.md](./34-part2-database-additions.md) is additive-only on top of it. Where a Part 2 design genuinely diverged from a Part 1 literal, the divergence was **recorded as an open item for the designated refresh agents** (§3.4, C1–C9) instead of silently applied. The single amendment to a Part 1-bound constraint (ScheduledCharge partial uniques, R-P9) is explicit, justified, flagged in three documents, and possible only because no DDL has shipped. The one edit made to a Part 1 file is the sanctioned pointer section "Part 2 additions" appended to the end of doc 13, which points to doc 34 and reinterprets nothing. Part 1 rows this register marks "answered" were answered **by choosing among the options Part 1 itself posed** — in the one case where Part 2 selected differently from a Part 1 leaning (Express over doc 01 §11's Standard), the selection is a documented ADR decision (ADR-037) with consequences enumerated, not a silent reinterpretation (§3.4 C9).

### 5.5 Standing constraints — preserved and strengthened

Verified against the security checklist in [32-financial-security-threat-assessment.md](./32-financial-security-threat-assessment.md), which audits every item below plus spec Part AB's automatic-rejection conditions:

- **Tenant isolation** — preserved and strengthened. All Revenue Engine provider objects live on the org's own connected account (Stripe-Account header), making cross-tenant payment identity structurally impossible, not merely policy; webhook tenancy resolves from **local references only** (`ConnectedAccount.providerAccountId @unique` + local anchor org match + metadata cross-check), and any mismatch quarantines the whole event; every new Part 2 model is org-scoped with a real Organization FK and placed in the ordered org-snapshot wipe (34 §12).
- **RBAC** — preserved. Every new permission is data in the `src/lib/permissions.ts` catalog (`revenue.*` org keys; `platform.connect.*` / `platform.fees.*` platform keys); no hardcoded role checks; platform-fee terms have **no org-scoped write route structurally**, enforced by static source-scan tests — spec Part AB's "platform fee editable by organization staff" rejection is satisfied by construction.
- **Financial controls** — strengthened. Webhook-truth-only settlement with exactly two writers for paid-state (static source-scan enforced); exactly-once anchored in database constraints with provider idempotency keys as a network-boundary defense only; append-only reversal records written in the same transaction that marks money moved; single-writer engines for notifications, failure classification, and fee math; no raw card or bank data anywhere (SAQ-A posture — no card-entry surface exists); money remains Decimal with explicit ISO 4217 currency.
- **Audit attribution** — preserved and strengthened. Every designed mutation calls `recordAudit`; provider-initiated facts carry `system:stripe-webhook` attribution; five new audit actions cover the payment-failure/return surface and one covers provider-fee recording; load-bearing decisions that cannot live in best-effort audit rows get durable append-only records (`CompensationReversalDecision`).
- **Existing aviation workflows** — untouched. No payment state reopens dispatch, reverses training records, or touches maintenance; financial pressure remains configured checkout restrictions only; operational closeout never waits on a payment provider.
